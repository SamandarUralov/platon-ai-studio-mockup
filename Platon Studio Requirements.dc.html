1. Product overview & vision

Problem

Operations teams run on spreadsheets, forms and ad-hoc scripts. Low-code tools help with screens but stall at real backend work: typed logic, queues, schedules, multiple databases, file storage and safe releases. Pure AI code generation is fast but produces code nobody on the team can review or maintain.

Vision

Platon AI Studio makes the whole application — Interface, Logic, Data, Storage — a single, versioned app definition that people edit visually and Studio AI edits through reviewable change plans. The same definition runs instantly on the Platon runtime, and can be exported as real code.

Users

PersonaNeeds
Builder (ops lead, analyst)Drag pages together, connect tables, set who sees what, preview as each role. Little or no code.
Platon developerTyped functions, APIs, crons and queues; SQL console; Git and CI/CD; code export.
Admin / ownerMembers, environments, credentials, releases to Production, audit.
App userUses the generated app (e.g. technicians, dispatchers). Never sees the Studio.

Product principles

  • Definition first. Everything the Studio edits is structured data. Canvas, flowcharts, JSON view and AI all read and write the same model.
  • Structure ships, records stay. Releases move structure (pages, schemas, functions, settings). Records, files, queue messages and run history never leave their environment.
  • AI proposes, people approve. Studio AI produces change plans that are previewed and applied, never silent edits.
  • Typed end to end. Function parameters, return values and API request/response shapes are declared, and connections between them are checked.
  • Plain language. Labels like “Who can call it”, “Delete files after 7 days” over infrastructure jargon.

3. Functional specification

3.1 Studio shell

  • Top bar: app switcher (search, recent apps, status, new app), layer tabs in order Interface · Logic · Data · Storage · Preview · Releases, environment and save status, profile menu (theme, language, logout), project settings.
  • Three-column layout per layer: left navigator, center workspace, right inspector / Studio AI. Both side panels collapse to icon rails (⌘, and ⌘\ hide panels; full-screen toggle). Panels auto-collapse on narrow windows.
  • Change log: every edit appends or updates a change entry (upsert by key) shown in Releases.

3.2 Interface layer

  • Left panel: “UI elements” title, Page components list (blocks on the current page, click to select), search, element tiles grouped Text & Layout, Data, etc. Add by drag-and-drop onto the canvas or double-click.
  • Canvas toolbar: page picker (pages & navigation), screen size presets and zoom, full-screen.
  • Canvas: blocks placed in rows; drop targets left/right/above/below; reorder with up/down/left/right controls; selection outline.
  • Right panel: properties of the selected element (Content, Style, Visibility sections). With nothing selected it shows the current page’s settings.
  • Pages: create with icon, name, route, “show in menu”, and per-role permissions. Sample app uses a left sidebar menu that collapses on mobile.
  • UI element form modal: name, icon picker, defaults. Open item: sizing of the icon picker.

3.2.1 Page logic (Code mode)

Every page has exactly one JavaScript file, its page logic. It owns the page’s client-side state, lifecycle hooks and handlers. Server work stays in the Logic layer; page logic calls it.

  • Design / Code switch in the canvas toolbar (next to Preview). Code replaces the canvas with the editor for the current page; the page picker switches files. Shortcut ⌘E.
  • Editor: line numbers, syntax highlighting, autocomplete for ctx.blocks.* (blocks on this page), ctx.data.* (tables), ctx.call() (saved Logic functions and APIs), ctx.state.*. Find, fold, format on save.
  • Left panel in Code mode: Outline (state, computed, hooks, handlers — click to jump), Page blocks (click to insert a reference), Available logic (functions and APIs with signatures).
  • Wiring is code only. Handlers bind to blocks inside the file via on: { 'ordersTable.rowClick': … }; the inspector does not edit events. Block ids are stable, so renaming a block title does not break bindings.
  • Problems strip under the editor: syntax errors, unknown block ids, unknown functions, wrong argument count, unused handlers. Release is blocked while errors exist.
  • Console tab: ctx.log() output and runtime errors from Preview for this page, with role and timestamp.
  • Studio AI in Code mode gets the file, the page’s blocks and Logic signatures as context and returns a diff to apply or discard.
  • Saving: same as Logic — unsaved dot on the page, Discard · Save (⌘S). A save writes one change ~ interface.pages.{id}.script.
  • Sandbox: runs in the browser only, no DOM access, no fetch; network goes through ctx.call() so access rules from §3.3 always apply.
export default definePage({
  state: { filter: 'open', selected: null },
  computed: { overdue: (ctx) => ctx.blocks.ordersTable.rows.filter(r => r.slaDue < Date.now()) },
  async onLoad(ctx) { await ctx.blocks.ordersTable.load({ status: ctx.state.filter }) },
  on: {
    'statusFilter.change': (ctx, v) => { ctx.state.filter = v; ctx.blocks.ordersTable.reload() },
    'assignBtn.click': async (ctx) => {
      const tech = await ctx.call('assignNearestTech', ctx.state.selected.id)
      ctx.toast('Assigned to ' + tech.name)
    }
  }
})

3.3 Logic layer

Left menu groups — Functions, APIs, Crons, Message Queues — each foldable, with item counts, status dots, unsaved-change markers and a hover “+” to create. A single search finds items across all four groups.

Functions (method builder)

  • A function is an ordered tree of layers: If, Switch, For each, Set variable, Return (logic); Select query, Execute query (data); HTTP request, MQ produce, MQ consume (integrations); and Function (call another saved function).
  • Layers are added by drag-and-drop or double-click from the left “Method layers” palette (searchable), dropped into any branch (Then/Else, cases, loop body), reordered by drag or move up/down, duplicated and deleted. Return layers cannot be moved via buttons, duplicated or deleted.
  • Three views: Builder, Flowchart (auto-laid-out, branches side by side, click to select) and JSON (copyable).
  • Signature: typed parameters (name, type, required) and a return type. object and array<object> types hold nested fields to any depth. Types: string, number, integer, boolean, date, datetime, enum, object, array<…>, file, any, row<table>, array<table>.
  • Return layer returns either a variable (any value set earlier — parameters, query results, loop items, function results; the last function result is the default) or a function call. Its source type is checked against the declared return type; mismatches, missing required fields and wrong argument counts are errors shown in the panel and as a badge on the layer.
  • Right panel tabs: Layer (configure selected layer or method settings) and AI assistant (prompt to add layers).

APIs

  • An API is a trigger whose layers are function calls. Saved functions are listed and searchable in the left panel; drag or double-click to add.
  • Settings in collapsible sections: Endpoint (method, path with :params), Access (Public / Basic auth / Token; anyone authenticated or only selected roles and permissions), Request · input (tabs Path, Headers, Query, Body; content type; field name, type, required; nested objects; generated example), Response · output (fields per status code 200/400/401/403/500 and content type, generated example).
  • Tabs: Problems (live validation: missing functions, argument count, undeclared input.x, used-before-set, unused parameters, access misconfigurations), Test (fill parameters, send, see status, time and body), Runs (history with status, environment, latency), History (unreleased changes then audit trail).

Crons

  • Name, cron schedule, timezone, Pause/Resume, Run now; body is a list of function calls (same builder as APIs).

Message queues

  • A queue is a channel between functions. Flow tab: Published by (auto-detected from MQ produce layers) → Queue (message fields) → Processed by (consumer functions, drag to attach). Dead-letter summary with Replay all.
  • Messages tab: recent messages with status (Waiting, Delivered, Retrying, Dead-letter), attempts, contents, Replay/Delete. Settings: message fields, concurrency, retries, backoff, time limit, in-order delivery.

Saving

Each Logic item tracks a snapshot on first edit. Header shows “Unsaved changes · Discard · Save” (⌘S). Discard restores the snapshot and removes its pending changes.

3.4 Data layer

  • Multiple database connections per app: PostgreSQL, MySQL, SQL Server, MongoDB, Redis. Connection form with test; credentials per environment.
  • Tables/collections with typed fields, relations and a relationship diagram; DDL view per dialect.
  • Test-data generation, SQL console (scoped to Development by default), record browsing.
  • Schema changes become migrations in releases; records never move between environments.

3.5 Storage layer

  • Object storage (MinIO / S3-compatible): connect any number of services (endpoint, region, TLS, keys per environment, test, disconnect). Buckets with purpose, objects, size, access (Private / Signed URLs / Public read) and versioning. Bucket file browser: upload, download, signed link, delete. “Used by” shows fields and functions that reference it.
  • Local storage: the app server’s filesystem under a root (e.g. /var/platon/fieldops on Ubuntu). Only declared folders are reachable. Per folder: size limit, function access (none / read / read & write), cleanup rule, nightly backup to object storage, file browser. Disk usage and a non-replication warning.
  • Functions address files as s3://{storage}/{bucket}/… or local://{folder}/…. Storage layers for the builder (upload, read, delete, signed URL) are planned.

3.6 Preview

Runs the app with Development data as a chosen role. Page and element visibility rules apply. Device sizes match the canvas presets.

3.7 Releases & environments

  • Pending changes list grouped by area (Pages, Logic, Database, Storage, Settings) with machine paths.
  • Create release (name, notes) → deploy to Development → Staging → Production; approval gate for Production; rollback to a previous release.
  • Release contents: definition diff, generated DB migrations, storage/bucket/folder provisioning. Never records, files, messages or run history.

3.9 Studio AI

  • Right-side panel in every layer, chat with history grouped by date, / command shortcuts, context-usage ring, chips for attached context (selected element, page, function).
  • Outputs change plans (pending → applied / discarded). In Logic, the assistant adds layers, attaches consumers or creates APIs; changes count as unsaved until saved.
  • Models: Claude and GPT via provider adapters, other models and local agents via MCP (§4.4).

4. Technical architecture

4.1 Stack

The chosen stack — Vue frontend and Spring Boot (Java) backend — fits well. Recommended specifics:

AreaRecommendation
Studio frontendVue 3 (Composition API) + TypeScript, Vite, Pinia, Vue Router, VueUse. Monaco for code/SQL/JSON. ELK.js for flowchart and ER layout. Own component library from the prototype’s tokens.
Generated app frontendVue 3 renderer that interprets page definitions; same renderer used by Preview.
BackendSpring Boot 3.3+, Java 21 (virtual threads), Spring Security (OIDC resource server), Spring WebSocket, Flyway, jOOQ for multi-dialect SQL and DDL generation, Testcontainers for tests.
IdentityKeycloak (or any OIDC provider) for Studio users; per-app user pools for runtime auth.
Platform DBPostgreSQL 16 (definitions as JSONB + relational metadata).
MessagingRabbitMQ default (native DLQ, retries, ordering via single-active consumer); Kafka adapter optional.
SchedulingQuartz in clustered JDBC mode (or db-scheduler).
Cache / presenceRedis.
StorageMinIO Java SDK (S3 API); local-filesystem agent on app servers.
SecretsHashiCorp Vault (SaaS); Kubernetes secrets or Vault for self-hosted.
ObservabilityOpenTelemetry, Prometheus, Grafana, Loki/Tempo.
DeployKubernetes + Helm (SaaS and enterprise self-hosted); Docker Compose for small self-hosted installs.

Additional recommendations: define the app definition as JSON Schema and generate both TypeScript types (frontend) and Java records (backend) from it, so the model never drifts. Use a sandboxed expression language (CEL) for conditions, arguments and values instead of SpEL or JavaScript. Kotlin is a reasonable alternative to Java if the team prefers it; it changes nothing else here.

4.3 Execution model (hybrid)

  • Interpreted (default): the Runtime loads the released definition and interprets pages, function layer trees, APIs, crons and queues. Deploys are definition swaps — seconds, no build.
  • Code export: the Release service generates a readable Spring Boot + Vue project (templates via JTE), commits it to the connected Git repo and can run it through CI/CD. Export is one-way; re-importing hand-edited code is out of scope for v1.
  • Both paths share the same validator so behaviour and errors match.

4.4 AI integration

  • Providers: adapters for Anthropic Claude and OpenAI GPT behind one interface (chat, tool use, streaming). Organization chooses default model; per-feature overrides.
  • MCP server: the Studio exposes tools to any model or local agent: read_definition, search_definition, propose_changes, validate, run_function_test, run_sql_dev, generate_test_data.
  • MCP client: projects can add external MCP servers (docs, ticketing, internal tools) the assistant may call.
  • Local agents: developers connect local agents (e.g. coding agents on their machine) via MCP with a personal token scoped to one project and environment.
  • Safety: AI writes only through propose_changes; plans are validated and shown before applying. Production data is never sent to models; SQL tools are limited to Development. Agent.md is included as project context.

4.5 Real-time collaboration

Edits are sent as change operations against a definition revision. The server applies them in order, rejects conflicting ops on the same node (client re-bases) and broadcasts to other editors over WebSocket. Presence (who is viewing which page or function) lives in Redis. Logic items lock softly while someone has unsaved changes.

6.2 Runtime: generated APIs

  • Base URL https://{slug}.{env}.platon.app (SaaS) or the customer’s host (self-hosted).
  • Pipeline per request: route → access (public / basic / bearer token; role or permission check → 401/403) → validation against request schema (path, headers, query, body; required and types → 400 with missing/invalid) → execute steps → shape response to the declared status schema → log run.
  • Errors in steps return 500 { "error": "runtime_error", "step": "s3", "message": … }; function timeouts return 504.
  • Rate limits per API and per token; CORS configured per app.

6.3 Runtime: function execution

  • Interpreter walks the step tree with a scoped context: input (validated parameters), variables set by into/set/loops, env, user, read-only secrets.
  • Expressions (conditions, args, values) use CEL; no arbitrary code. SQL in select/execute is parameterised from :name bindings only.
  • Limits per run: timeout (declared), max steps, max loop iterations, memory, HTTP egress allowlist per app.
  • Every run produces a trace (step, duration, inputs/outputs truncated) for Test and Runs.

6.4 Runtime: crons & queues

  • Crons: Quartz cluster, one execution per schedule across nodes, missed-fire policy “run once”, pause/resume per environment.
  • Queues: RabbitMQ exchange + queue per definition queue and environment; consumers are functions; retries with fixed or exponential backoff then dead-letter queue; in-order option uses a single active consumer; message schema validated on produce.

6.5 Runtime: storage

  • Object storage via S3 API: private by default, signed URLs (default 1 hour), public read only when set on the bucket.
  • Local folders via an agent on each app server: path confinement to declared folders, quota enforcement, cleanup job, nightly backup to the configured object storage.

7.2 Availability & recovery

  • SaaS Studio and runtime: 99.9% monthly. Zero-downtime deploys of the platform.
  • Platform DB: point-in-time recovery; RPO ≤ 15 min, RTO ≤ 1 h. Release rollback ≤ 2 min.
  • Self-hosted: HA Helm profile (≥ 2 replicas per service) and single-node Compose profile.

7.3 Security

  • Tenant isolation: organization id on every row, row-level security in PostgreSQL; per-environment runtime namespaces.
  • Studio roles (Owner, Admin, Editor, Viewer); Production deploy and secrets restricted to Admin/Owner.
  • Secrets in Vault, referenced only by secret://; never returned to the browser after save (masked, rotate only).
  • Sandboxed execution: CEL expressions, parameterised SQL, egress allowlist, resource limits; no user-supplied code in v1.
  • Audit log for every change, save, release, deploy, secret access and AI plan application.
  • TLS everywhere; encryption at rest for platform DB and object storage.
  • AI: no Production records or secrets in prompts; per-org opt-out of model providers; local-agent tokens scoped and revocable.
  • No compliance certification required yet; keep data model GDPR-ready (export, delete, data residency per region).

7.4 Other

  • Observability: traces across Studio API → Runtime → connectors; per-app dashboards (requests, errors, latency, queue depth, cron runs).
  • Internationalization: Studio UI and generated apps localized; Studio ships in English first.
  • Accessibility: WCAG 2.1 AA for the generated apps; keyboard support for the Studio canvas and builder.
  • Browsers: latest two versions of Chrome, Edge, Firefox, Safari; Studio desktop-first (≥ 1024 px), generated apps responsive.
  • Testing: JSON Schema contract tests between frontend and backend; interpreter golden tests per step type; Testcontainers for each database dialect.

8. Decisions to confirm

  • RabbitMQ as the default broker, with Kafka as an optional adapter.
  • CEL as the expression language for conditions and arguments.
  • Code export is one-way in v1.
  • Billing and plan limits (projects, environments, runs) are not covered here.
  • Whether self-hosted installs may use external AI providers or only local models.
